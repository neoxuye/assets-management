## 一、系统定位与设计哲学

### 1.1 核心目标
构建一个**基于宏观基本面驱动**、**结合数据量化验证**、**具备抗人性弱点能力**的投资决策支持系统。它不是一个黑盒交易机器，而是一个用于辅助人类专家做出更理性决策的"副驾驶"。

### 1.2 设计哲学 (First Principles)
1.  **宏观驱动 (Macro-Driven)**: 资产价格的长期走势是由增长、通胀、流动性等宏观因子决定的。
2.  **概率思维 (Probabilistic)**: 不预测单一未来，而是计算多种情景下的最优解。
3.  **防御优先 (Defense First)**: "活下来"是复利的前提。系统内置 VIX 熔断机制，强制在高风险环境下降低敞口。
4.  **透明可释 (Transparent)**: 每个评分和权重都必须有明确的逻辑来源（可追溯到具体因子贡献）。

## 二、核心文档体系 (Documentation Strategy)

为了防止文档与系统代码脱节（文档腐化），本项目采用 **"Code-First, Doc-Reflect"** 的维护策略：

### 2.1 唯一事实来源 (Single Source of Truth)
*   **算法逻辑**: 以 `js/algo_*.js` 代码为准。
*   **核心常量**: 以 `js/data.js` (如 `macroStdDev`) 为准。
*   **文档定位**: 文档是对代码逻辑的**解释与概括**，而非独立定义的源头。

### 2.2 文档结构
| 目录 | 关键文件 | 用途 | 维护频率 |
|------|----------|------|----------|
| **01_Core_Reference** | `02_Algorithm_Bible.md` | **圣经**：所有算法聚合，必须与代码严格一致 | 🔥 每次算法变更 |
| | `03_Data_Dictionary.md` | 数据词典：参数定义合集 | 月度 |
| | `01_System_Architecture.md` | 顶层设计：系统全貌 | 季度 |
| **02_Architecture** | (专题研究) | 如《评分算法说明》等具体研究案 | **归档后不更新** |
| **03_Reference** | (参考资料) | 如《历史参数验证表》等静态数据 | 不定期 |
| **99_Archive** | (历史遗迹) | 旧版本文档 | **只读** |

### 2.3 防腐化机制 (Anti-Rot Protocol)
1.  **变更同步**: 任何修改 `algo_*.js` 逻辑的 Pull Request/Commit，**必须**同步更新 `Algorithm_Bible.md`。
2.  **定期审计**: 每月进行一次"Code vs Doc"抽查（检查常量、公式系数是否一致）。
3.  **就地归档**: 一旦某个专题研究文档（如Docs根目录下的散乱文件）被整合进 Core Reference，原文件应立即移入 `99_Archive`，避免误导。

## 四、核心模块说明

### 4.1 评分引擎 (Scoring Engine)
*   **位置**: `js/algo_v16.19.js`
*   **逻辑**: 基于宏观因子偏离度（Z-Score）和资产敏感度计算得分。
*   **关键特性**: 内置 Z-Score 标准化、非线性惩罚（如滞胀期打压）。

### 4.2 配置引擎 (Allocation Engine)
*   **位置**: `js/core_v16.15.js` (P1 Layered Weights)
*   **逻辑**: 基于 VIX 水平动态调整 风险/避险/交叉 资产池的预算上限。
*   **关键特性**: "Cut the tail" —— 在高波动率下强制降低风险资产上限。

### 4.3 数据中心 (Data Center)
*   **位置**: `js/data.js`
*   **逻辑**: 存储当前宏观参数、历史场景快照、资产元数据。
*   **关键特性**: 单一数据源，前端 UI 和算法共享同一份数据定义。

## 二、核心代码执行流与文件定位

### 1. 从数据输入到推荐生成的全流程（P1 主线）

用户在界面点击“生成推荐配置”（或批量测试触发），代码的生命周期如下：

1. **宏观输入提取**
   - 依赖项主要在 `ui_v16.js` 获取。
   - 核心逻辑由 `core_v16.18.js` 中的 `getMacroValues()` (L252) 和 `validateMacroParams()` (L108) 负责读值和边界审计。

2. **打分计算 (Scoring)**
   - 遍历各大类资产，调用 `calcAssetScore(majorKey, macroVals)` 或 `calcAssetScore_v98`。
   - **文件位置**: `algo_v16.19.js` (算法核心，约 L1000+ 起)
   - **附加估值调节**: `core_v16.18.js` 中 `applyValuationAdjustment()` 处理 P/E 等均值回归逻辑。

3. **混合与制度调节 (Regime Detection)**
   - **文件位置**: `core_v16.18.js` -> `detectMacroRegime()`。
   - 检测市场阶段（如 `stagflation`，`volatility_crisis` 等），并通过 `applyReasonBonus` 施加惩罚。

4. **P1 权重生成 (Weight Allocation)**
   - 历史中我们习惯称之为 `P1_calculateLayeredWeights`。**实际上系统中并没有这个独立函数**。
   - **真实位置**: 
     - 界面交互中，在 `algo_v16.19.js` 的 `recalculateWeightsForSelectedAssets()` 里执行。
     - 批量盲测中，在 `ui_v16.js` (L7005+) 的 `batchTest` 循环里，直接用 `p1Weights[k] = s / totalP1Score` 进行归一化比例分配。

5. **风险偏好上限限制**
   - **功能**: 根据用户选的保守/平衡/激进，强制限制风险资产敞口上限。
   - **文件位置**: `core_v16.18.js` -> `applyRiskPreferenceLimits(weights, riskPref)`

6. **换手与权重稳定性约束**
   - **功能**: 防抖，避免微小的宏观数据变化导致全盘重调。
   - **文件位置**: `core_v16.18.js` -> `applyWeightStability()`

---

### 2. Black-Litterman 引擎支线（风控型分配）

这是系统的替代分配路径，也是压舱石对比层。

1. **基本面配置**
   - **文件位置**: `bl_engine.js` 头部。
   - **核心参数**: `BL_CONFIG` (`tau=0.25`, `delta=2.5`, `maxView=0.08`, `maxWeight=0.30`)

2. **协方差与均衡权重支持**
   - **文件位置**: `bl_covariance.js`
   - 为引擎提供长期协方差（已内嵌真实 ETF 60个月收益计算而来的协方差矩阵），结合 VIX 进行危机时的动态相关性放大 `adjustCovForVix`。

3. **评分映射为观点矩阵 (P & Q)**
   - **功能**: 把 P1 产出的 0-100 评分转化为 BL 能识别的“预期收益”和“信心度”。
   - **文件位置**: `bl_engine.js` -> `buildViewMatrices()`

4. **BL 后验与最优化输出**
   - **功能**: 计算后验协方差和收益向量，按目标函数（二次规划/MVO近似）求出最优权重。
   - **文件位置**: `bl_engine.js` -> `calculateBLPosterior()` -> `optimizeWeights()`
   - **注意**: 最终输出为降低模型敏感性，采用了 60% MVO + 40% 均衡基准(Equilibrium) 的混合，这是导致 BL 收益表现偏向保守的核心制约因素。

## 三、排错与寻找函数准则 (For AI or Developer)

- **UI 层交互或渲染** (按钮回调，DOM 更新, 报表输出, ECharts 图表，批量盲测报告展示)：**全部**在 `ui_v16.js` 中找。
- **算法基准与各资产评分细则** (某一项利率具体扣多少分，PDI的敏感度矩阵)：在 `algo_v16.19.js` 找。
- **核心工具类、系统制度、上限风控边界、数据获取与清理持久化**：在 `core_v16.18.js` 找。
- **协方差极值、权重大幅收缩保守不输出**：找 `bl_engine.js` (算法问题) 和 `bl_covariance.js` (数据源质量问题)。

> 💡 **进阶避坑指南**：以后如果找不到某个功能对应的函数，请不要盲猜名字去 grep，而是**按功能所属的执行流和生命周期**，直接对准第一部分总结的核心文件去扫描大纲或使用关键词 `function` 筛选定位。
